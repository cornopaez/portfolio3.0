### Important environment note for future steps
This project lives on a **network-mounted SMB share** (`//mauriciopaez@rpi5.cornopaez.net/Rome`, a Raspberry Pi 5 NAS, ZFS pool of 3x 8TB HDDs in a mirror, no SLOG device, served via Samba, both machines on 1GbE Ethernet), not local disk. This causes real, recurring flakiness: corrupted `node_modules` entries mid-install, `rm -rf` hitting "Resource busy", a hung `ssr-dev-server` file watcher, and — most seriously — the esbuild-based `application` builder consistently crashing with SIGABRT under full-build load (see the v19 section below). A trivial isolated `esbuild.build()` call works fine; only sustained/heavy concurrent file I/O seems to trigger it.

Diagnosed further during v21: `arc_summary` on the NAS shows a healthy ARC (97.5% hit rate, 99.8% on metadata) — ruling out ARC/cache-pressure as the cause. `zpool iostat` during a stall showed only sporadic bursts, not sustained saturation, arguing against raw disk throughput being maxed out either. The pool has **no SLOG** (`Transactions to SLOG storage pool: 0 Bytes`), so every sync write (fsync) has to hit the mirrored HDDs directly — plausible source of bursty stalls correlated with write-heavy operations (npm installs, build output). The user has also independently observed `smbd` spiking to 100% CPU during stalls, and separately sees macOS randomly disconnect this same mount (and other USB peripherals) outside of any Angular-CLI activity — so this may be a broader macOS/USB-controller or SMB-client issue on this specific machine, not purely NAS-load-driven. Root cause is still not fully confirmed. If something inexplicably hangs or crashes, suspect the volume/mount before the code — retry once or twice (or reboot, which has resolved it before), and prefer the legacy webpack builder over the esbuild `application` builder on this machine until/unless this is understood.

**Asked the user how to proceed; they chose to pause the upgrade here** rather than decide immediately between:

2. Swap to an actively maintained alternative (e.g. `recaptcha-angular`, found on the registry, actively published) — bigger change, touches `contact-form.component.ts` and its module wiring, not just `package.json`.

### v19 — done, and a real detour worth reading before v20/v21

`npx ng update @angular/core@19 @angular/cli@19 --allow-dirty` itself succeeded cleanly (no peer-dep conflicts, now that `ng-recaptcha` is gone). But the resulting build failed with `NG8002`/`NG8001` errors ("routerLink"/"router-outlet"/"ngClass" not recognized) on a handful of components, and re-running the build showed a *different* subset of failing components each time — looked exactly like the kind of flaky compiler bug that would justify migrating off the legacy webpack builder.

**That appearance was misleading.** The real cause: `src/app/app.module.ts` had `BrowserModule.withServerTransition({ appId: 'serverApp' })` in its `imports` array, and that method no longer exists on `BrowserModule` in Angular 19. Because that one array entry fails static analysis, the *entire* `imports` array becomes unresolvable to the compiler, so every component that uses `routerLink`/`router-outlet`/`ngClass` loses access to those directives. The "flakiness" was never real — every run always had the same full list of affected components, but I was only ever looking at the tail end of a long truncated error list, so different runs' tails looked different. Fix: plain `BrowserModule`. Separately, `@types/node` (still `^12.20.12`) was too old for `@angular/ssr/node`'s own `node:http`/`node:http2` type references — bumped to `^20.19.0`.

**Before finding that**, acting on the (wrong) flaky-builder theory, I ran the "migrate to new build system" optional migration (`ng update @angular/cli --name use-application-builder`, needed `NG_DISABLE_VERSION_CHECK=1` + pinning to the local v19 CLI binary to avoid it fetching a Node-22-requiring v22 CLI). That migration itself completed and, combined with the two real fixes above, produced a build with **zero compile errors**. But actually running that build consistently crashed the Node process with `SIGABRT` (exit 134) under the esbuild pipeline's full-app load — reproduced 3+ times, including with `NG_BUILD_MAX_WORKERS=1`/`UV_THREADPOOL_SIZE=1`. Isolated a single trivial `esbuild.build()` call to confirm esbuild itself isn't broken (it succeeded); a plain `find node_modules -path ...` also hung once during this investigation. This points at the network-mounted volume (see the note near the top of this file) failing under esbuild's concurrent I/O pattern specifically, not a code problem.

Once the real bug was found, the need for the application-builder migration evaporated, so **it was reverted**: restored `server.ts` (repo root), `angular.json`, `tsconfig.app.json`, `tsconfig.server.json`, and `package.json`'s scripts section from `HEAD` (git show), keeping only the real fixes (`BrowserModule`, `@types/node`) plus the already-committed v19 package versions. One more small break surfaced by `esModuleInterop: true` (added by the aborted migration to the base `tsconfig.json`, kept since it's harmless): `server.ts`'s `import * as express`/`import * as bodyParser` had to become default imports. Confirmed clean after that — browser build, SSR build, 59/59 tests, `dev:ssr` smoke test (including a direct check that the Turnstile widget still renders correctly on the contact form).

**Verdict for later:** the application-builder migration is likely still worth doing eventually (it's the officially recommended direction, and the legacy webpack builder won't be supported forever), but not blindly on this machine/volume — try it again once the network-mount flakiness is understood or the project is on local disk. Not required to reach v21.

**Two real bugs found and fixed** (both real, pre-existing/newly-enforced issues, not upgrade artifacts to revert):
1. `src/app/projects/projects-home/projects-home.component.html` had `[style.backgroundImage]="'url(' + project.card.background_image + ')'"` — `background_image` never existed on the `ProjectCard` type (only `title`/`subtitle`/`custom_html`/`image`/`icons`/`card_class` do; confirmed against real API response data). v21's template type-checking is stricter and now catches it. This binding has always evaluated to `url(undefined)` and done nothing — the real per-project background comes from the `card_class`-driven SASS files in `project_posters/`, and there's a separate working `@if (project.card.image) { <img> }` block already using the real `image` field. Fixed by removing the dead binding entirely (not by guessing a replacement value) since it was never functional and nothing observable depends on it.
2. **New in `@angular/ssr` at this version**: `CommonEngine` now validates the request's `Host` header against an `allowedHosts` allowlist and *silently falls back to client-side rendering* (200 OK, but just the static unrendered shell) if the host isn't recognized — confirmed via the compiled server's console output: `ERROR: URL with hostname "localhost" is not allowed... Falling back to client side rendering.` This is why a `dev:ssr`-style smoke test would show a 200 with the generic `<title>Portfolio 3.0</title>` shell, no `<ngx-turnstile>` markup, and no rendered project cards — none of that is a real regression, it's this new gate silently swallowing SSR. Fixed in `controllers/home.ts` by constructing `CommonEngine` with `{ allowedHosts: ['localhost', 'cornopaez.com', 'www.cornopaez.com'] }` (production domain taken from `environment.prod.ts`'s `baseUrl`).
3. **Found after the `allowedHosts` fix, on re-verify**: `/Projects` (the one route with an `HttpClient`-backed resolver) still returned the CSR shell. Server console showed Angular's own `NG02801` warning (`HttpClient` not configured to use `fetch` for SSR) immediately followed by `ERROR TypeError: Converting circular structure to JSON`, thrown while the XHR backend tried to serialize a failed request's error object — this is the deprecated SSR XHR backend, not something `allowedHosts` touches. Fixed in `src/app/app.module.ts` by adding `withFetch()` to the `provideHttpClient()` call (`provideHttpClient(withFetch(), withInterceptorsFromDi())`), per Angular's own recommendation in the warning text.

**Verified**: browser build (0 errors), SSR server build (0 errors), all 59 unit tests, and a live smoke test of the compiled server bundle (`PORT=4200 node dist/portfolio3/server/main.js`, not `dev:ssr` — same rationale as v17/v20, avoids the flaky watch-mode file watcher on this volume) across all 4 major routes: `/` and `/Contact` render correctly, `/Projects` renders real Mongo-backed content (confirmed via `<h3>` project titles and `class="<card_class> project"` divs — note the class order is `card_class` then `project`, reversed from how the template source reads, since Angular's renderer doesn't preserve static+binding class token order), and `/About`.
