## Phase 4: Express 4 → 5 — done
- `server.ts`: replaced `body-parser` (which wasn't even a declared dependency — only present via hoisting from a transitive dep, a latent fragility) with Express's own built-in `express.json()`/`express.urlencoded()`.
- Fixed the two bare-wildcard routes for Express 5's path-to-regexp v8, which dropped support for unnamed `*`/`*.*` patterns:
  - `server.get('*.*', express.static(...))` → `server.use(express.static(distFolder, { maxAge: '1y', index: false }))`. Switched from a path-restricted `.get('*.*', ...)` to unconditional `.use(...)` middleware (the standard/robust pattern — `express.static` itself no-ops and calls `next()` for paths it can't find on disk, so this isn't a widening of what actually gets served). **Caught in testing**: without `index: false`, `express.static`'s default directory-index behavior intercepted `/` and served the static, unrendered `index.html` shell directly — completely bypassing SSR silently (200 OK, but the generic `<title>Portfolio 3.0</title>` shell, not the real page). `index: false` fixes this so `/` correctly falls through to the SSR catch-all below.
  - `server.get('*', home.home)` → `server.get('/{*splat}', home.home)`. Named wildcards in path-to-regexp v8 require at least one path segment by default and don't match the bare root — **also caught in testing** (`/` returned a 404 with plain `/*splat`). The `{...}` brace syntax makes the wildcard segment optional, restoring the old `'*'` behavior of matching everything including `/`.
- Bumped `express` 4.22.2 → 5.2.1, `@types/express` 4.17.25 → 5.0.6.
- `controllers/data.js` (named-param routes only, `/contact`, `/projects`, `/:name`) and `controllers/home.ts` (no route patterns, just a handler function) needed no changes — confirmed by reading both.
- Hit a stale Angular/webpack build cache mid-phase (`Module not found: Can't resolve './debug'` inside express's bundled `debug` package, despite the referenced files existing on disk with correct content) — a known quirk of this network-mounted volume (see `ANGULAR-UPGRADE-PROGRESS.md`). Fixed by `rm -rf .angular/cache dist/portfolio3` and rebuilding; not a real code issue.
- Verified: browser build ✓, SSR build ✓, 59/59 unit tests ✓, `npm run lint` unchanged at 96, Playwright e2e ✓, and a full live-route smoke test against the compiled server bundle: `/` (real SSR content, correct title/h1), `/main.js` (static asset, 200), `/data/projects` (200), `/Projects` (real SSR content, 4 project cards), `/About` (200), `/Contact` (200), and an unmatched path (200, falls through to Angular's client-side Error route as expected).

## Phase 5: MongoDB driver 3 → 7 — done
- Rewrote the three callback call sites to the Promise/`await` API (removed in driver v4+): `MongoClient.connect(url, options, callback)`, `cursor.toArray(callback)` (`getProjectsCards`), `insertOne(query, callback)` (`postContactRequest`). Each function's external contract (still returns a `Promise`) is unchanged, so `controllers/data.js` needed no edits.
- Dropped the now-inert `useUnifiedTopology` option entirely.
- Incidental fixes made naturally while rewriting `connect()` (not scope creep — directly in the lines being touched): removed unused `express`/`assert` requires; replaced the internal/undocumented `db.s.options.dbName` property access with the driver's own public `client.db()` (no-args — returns the database named in the connection string's path, exactly equivalent but using documented API instead of poking at driver internals). The rewritten `async`/`try`-`catch` version also naturally no longer has the `todo.md` item 5 bug (missing `return` after `reject(false)` causing a `TypeError` fall-through on connection failure) — same incidental-fix precedent as the Angular v17 step.
- **Real bug found via the mocha integration tests** (first time they'd been run all session): `mocha-tests/mongo-queries.test.js` called `ObjectId(insertResponse.insertedId)` without `new` — driver v3 allowed calling `ObjectId` as a factory function, but it's a proper ES6 class in modern versions and throws `TypeError: Class constructor ObjectId cannot be invoked without 'new'`. Fixed by adding `new`. Also fixed `require('mongoDb')` (wrong casing, line 6 of the same file) → `require('mongodb')` — only worked before by accident of this project's case-insensitive network volume; would have failed outright on a case-sensitive filesystem (e.g. Heroku's Linux dynos).
- **False alarm along the way, worth recording**: the first `npx mocha mocha-tests/*.test.js 2>&1 | tail -50` run appeared to hang indefinitely (8+ minutes, no output). Root cause was **not** a real hang: (1) `| tail -50` buffers all output until the piped process hits EOF, so nothing prints until mocha's process actually exits; (2) mocha doesn't force-exit by default, and leftover MongoDB driver connection-pool handles kept the Node process alive after the tests had already finished running. Confirmed via an isolated diagnostic script (bare `MongoClient.connect()`, then the rewritten `mongo-connection.js` module directly) that the actual connection resolves in ~200ms — no real hang anywhere. Re-ran with `mocha ... --exit --timeout 10000` (no `tail`) and got immediate, correct output. Worth remembering for future mocha runs on this project.
- Verified: browser build ✓, SSR build ✓, 59/59 unit tests ✓, all 6 mocha integration tests ✓ against the real Atlas cluster, live-route smoke test of `/Projects` (real content, 4 cards), `/data/projects`, `/data/:name`, and `/Contact/form` (renders with the Turnstile widget present) against the compiled server bundle.

## Phase 6: Helmet 3 → 8 with explicit CSP — done
- Bumped `helmet` 3.23.3 → 8.3.0. Helmet 4+ enables a restrictive default CSP (v3 enabled none), so `server.ts`'s bare `helmet()` needed real directives for every external resource this site actually loads.
- Used Playwright (already in the toolchain from Phase 3) to script a real-browser check across `/`, `/Contact/form`, `/Projects`, `/About` — navigate, collect console errors, flag anything CSP-related. This caught real, concrete violations no amount of static grepping would have found:
  - Three Google Fonts `@import url(...)` stylesheets in `src/styles.sass` (Roboto, Cinzel/Merriweather, Open Sans/Raleway) — not visible in `index.html`, only in compiled component-level CSS. Added `https://fonts.googleapis.com` to `styleSrc` and `https://fonts.gstatic.com` to `fontSrc` (the actual font files Google's stylesheet references).
  - `script-src-attr 'none'` (Helmet's default) blocked an inline event-handler attribute injected at runtime by one of the third-party scripts (Bootstrap/jQuery/a widget — not present in this repo's own template source, confirmed by grep). Added a narrow `scriptSrcAttr: ["'unsafe-inline'"]` allowance — deliberately kept separate from `scriptSrc` itself, which stays locked down to specific origins (no blanket inline-script execution allowed).
  - Re-ran after both fixes: **zero CSP violations** across all four routes.
- Verified the fix didn't just silence errors but that things actually render correctly: checked real computed styles in the browser (`.nav-link` font-family is "Raleway", body font-family is "Open Sans", `.btn-dark` displays correctly) — confirms Bootstrap and the Google Fonts imports are genuinely working, not just failing silently.
- One remaining console error on `/Contact/form` (`Failed to load resource: 400` from `challenges.cloudflare.com/cdn-cgi/challenge-platform/...`) — confirmed this is Cloudflare's own bot-detection response to headless-browser automation, not a CSP issue: it's not one of our directive origins, and it appeared identically before and after the CSP fix. Same category of limitation noted during the original Turnstile integration — genuine widget behavior for a real human visitor can't be fully verified via headless automation, only via a live browser.
- Final CSP directives in `server.ts`: `scriptSrc` (jQuery, Popper/cdnjs, Bootstrap CDN, Font Awesome Kit, Cloudflare Turnstile), `scriptSrcAttr` (inline handlers), `styleSrc` (Bootstrap CDN, Font Awesome, Google Fonts, `'unsafe-inline'`), `fontSrc`/`imgSrc` (Font Awesome, Google Fonts assets), `connectSrc`/`frameSrc` (Turnstile).
- Verified: browser build ✓, SSR build ✓, 59/59 unit tests ✓, `npm run lint` unchanged at 96, Playwright e2e ✓, zero CSP violations on all 4 major routes with real rendering confirmed.

## Phase 8: Final sweep — done

- **Removed `guess-parser`** (devDependency): confirmed via `npm ls guess-parser` it was a top-level, unreferenced dependency — nothing else in the tree pulls it in, and nothing in this project's own code requires it (grepped `src/`, `controllers/`, `middlewares/`, `server.ts`). Same dead-weight pattern as `socket.io`/`loadtest` in Phase 1. Removing it dropped the `@wessberg/ts-evaluator` → `jsdom` → `http-proxy-agent` → `@tootallnate/once` vulnerability chain entirely. **Did not** remove `browser-sync` even though it also shows an unfixable vulnerability (`immutable`) — confirmed via `node_modules/@angular-devkit/build-angular/package.json` that it's declared as a genuine peer dependency of Angular's own SSR dev-server tooling (used by `npm run dev:ssr`), not dead weight; removing it risks breaking that workflow.
- **Final `npm audit`: 39 vulnerabilities (2 low, 9 moderate, 26 high, 2 critical)** — down from the 53 baseline at the start of this effort. Ran `npm audit fix` repeatedly throughout every phase; what's left is fully traced and categorized, not unexamined:
  - **The overwhelming majority trace to `protractor@7.0.0`, still bundled as a direct dependency inside `@angular-devkit/build-angular@21.2.19` itself** (confirmed via `npm ls protractor` back in Phase 3) — independent of whether this project uses the protractor builder (it doesn't, since Phase 3). This single root cause accounts for: `adm-zip`, `form-data`, `qs`, `tough-cookie`, `tmp`, `xml2js`, most of `uuid`, and a shared `brace-expansion`/`glob`/`minimatch` chain. Nothing to do here short of Angular's own team dropping protractor from their tooling package — not something a downstream project can fix.
  - **`postcss`** — bundled directly inside `@angular-devkit/build-angular` itself. Same category: Angular's own tooling, no fix available, out of this project's control.
  - **`@hono/node-server`** — via `@modelcontextprotocol/sdk`, a dependency of `@angular/cli` itself (their newer MCP/AI-tooling integration). `npm audit fix --force` would *downgrade* `@angular/cli` to 21.0.4, undoing the just-completed Angular 21 upgrade — declined.
  - **`diff`/`serialize-javascript`** (via `mocha`'s own transitive deps) — `npm audit fix --force` would downgrade `mocha` to 8.1.3, undoing this session's mocha 10→11 bump — declined, not a net improvement.
  - **`immutable`** (via `browser-sync`) — see above; a real Angular-tooling peer dependency, not removable without risking `dev:ssr`.
  - **`uuid`** (partial, via `sockjs`/`webpack-dev-server`) — Angular's own dev-server tooling (`ng serve`'s live-reload), same category.
  - None of these are reachable from this app's actual runtime code path (`server.ts`, `controllers/`, `middlewares/`, `src/app/`) — they're all in build-time/dev-time tooling dependency trees, not code that ships to production or handles real requests.
- **Full final verification pass** (mirroring the Angular upgrade's final pass):
  - Default config: browser build ✓, SSR build ✓, 59/59 unit tests ✓, 6/6 mocha integration tests ✓ (real Atlas cluster), `npm run lint` unchanged at 96 findings, Playwright e2e ✓.
  - **Production config** (`ng build --configuration production` + `ng run portfolio3:server:production`, the actual `heroku-postbuild` path): both build cleanly.
